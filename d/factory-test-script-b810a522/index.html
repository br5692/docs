Factory.ai · Partner Portal · Manual test script

Weeks 1 to 5, by hand

Walk this top to bottom on the hosted stack. Each row is one check with what to do, what should happen, and where to confirm it. Note anything off in the right-hand column. Ordered the way the Tuesday walk-through runs.

00

Before you start

  • Portal for Weeks 1 and 2: https://factory-partner-portal.pages.dev (Week 2 build). Portal for Weeks 3 to 5: https://latest.factory-partner-portal.pages.dev (all weeks; same sign-in, same data). Salesforce: the partial sandbox, Factory Sales app, Partner Applications tab from the App Launcher.
  • Use a fictional company and a test address you own. Nothing here emails anyone else.
  • Two paths for the two emails (invite and sign-in link). Path A, real inbox: deliverability set to All email in the sandbox and the hosted mail transport switched to Salesforce for the hour; both revert after. Path B, no email: the link is read from the hosted service log instead. Say which path before you start; the rows below say where each applies.
  • Weeks 1 and 2 take about 45 minutes. Weeks 3 to 5 add about 40 minutes and need the same approved partner from Week 2. Two full passes on different days is a solid review.
Rate limits. Five sign-in requests per address and twenty per network address per hour. If you hit them, the reply looks the same, and the next hour clears it.

Set up on a new machine

Everything a tester, or Claude Code, needs to run the portal locally and the tests against the sandbox. Self-contained; paste this section into a Claude Code session and it can do the setup. The hosted addresses in section 00 need none of this.

Addresses

  • Code: https://github.com/br5692/factory-partner-portal (private; ask for access). Everything below runs from a clone of it.
  • Portal, Week 2 build: https://factory-partner-portal.pages.dev. Portal, all weeks: https://latest.factory-partner-portal.pages.dev.
  • Web service health: https://factory-partner-portal-tool-layer.onrender.com/health?deep=1 (reports the deployed commit and whether Salesforce answers).
  • Salesforce partial sandbox: https://factoryai--partial.sandbox.my.salesforce.com, app Factory Sales, tab Partner Applications. Sandbox logins go through https://test.salesforce.com.
  • Reference pages: progress by week with clips, decisions log, how Week 2 fits together.

Prerequisites

  • git, Node 22 or newer, pnpm 10.12.4 (corepack enable && corepack prepare pnpm@10.12.4 --activate), Salesforce CLI (npm i -g @salesforce/cli).
  • A Salesforce sandbox user with the Portal Admin Fields permission set for operator steps, and a second user without it for the permission checks. Ask for both.
  • The .env file. It holds the sandbox connection (SF_LOGIN_URL, SF_INSTANCE_URL, SF_CLIENT_ID, SF_USERNAME, SF_JWT_PRIVATE_KEY, SF_API_VERSION), the bearer keys (TOOL_LAYER_API_KEYS), SESSION_SECRET, PORTAL_URL and the mail and rate-limit settings. It is never in the repo or in this page; ask for it and keep it out of git. .env.example in the repo lists every name with a comment.

Commands, in order

git clone https://github.com/br5692/factory-partner-portal.git
cd factory-partner-portal
pnpm install
cp /path/to/.env .env            # the file you were given, never commit it
set -a; . ./.env; set +a

# Salesforce CLI login to the sandbox (opens a browser; pick the alias below)
sf org login web -a factory-partial -r https://test.salesforce.com
# The sf CLI breaks when SF_API_VERSION is exported; run it with the variable unset:
env -u SF_API_VERSION sf org display -o factory-partial

# Checks that must be green before any manual pass
pnpm -r typecheck
pnpm -r build
pnpm -r test                     # unit suites; contract suites run only when the SF_* variables are set

# Local stack (two terminals). MAIL_TRANSPORT=log prints sign-in links to the terminal instead of emailing.
cd tool-layer && MAIL_TRANSPORT=log PORT=8080 SIGN_IN_REQUIRES_CONTRACT=false npx tsx src/index.ts
cd portal && VITE_PORTAL_WEEK=2 npx vite --port 5173      # 2 shows Week 2 only; 3, 4, 5 show later weeks

# Then open http://localhost:5173 and run the script against it. Local service: http://localhost:8080/health?deep=1

Things that trip people up

  • Path B sign-in links: locally they are printed by the service as a JSON line with "event":"sign_in_email" and a link. On the hosted stack they are in the Render service log (service factory-partner-portal-tool-layer); ask for Render access or use Path A.
  • Path A emails: Setup, Email, Deliverability, Access level All email in the sandbox, and the hosted service's MAIL_TRANSPORT set to salesforce. Both revert after the session. Only send to addresses you own.
  • Rate limits: five sign-in requests per address and twenty per network address per hour. Locally, restarting the service clears them.
  • The main portal address stays at Week 2 on purpose. Weeks 3 to 5 need the preview address or a local portal started at that week.
  • Operator steps in Weeks 2 and 5 need the permission set; use Setup, Users, Login As for the test operator rather than sharing passwords.
  • Every test record you create should start with [TEST] in its name so it is easy to find. Leave them; nothing needs deleting.
