Week 1 briefing

Six things were built in Week 1. Nobody should memorise 47 fields before a call. Keep this open instead. Each item gives one line to say, the detail underneath if the room pushes, and the exact place to click if somebody wants to see it.

How to use it. Read only the bold line out loud. Stop there. Most of the room wants the one line.

If a question comes back, the bullets under it are the answer, in the order they are usually asked.

If somebody wants proof, the last line of each item is a link that opens the thing itself. Opening it live is stronger than describing it.

The whole week in one line

“Week 1 is the foundation everything else sits on: the data model inside your org, a service that talks to it, a sign-in that uses no password, and a record of every single call.”

If the call only has room for one sentence about Week 1, that is the sentence. The six items below are the same thing at more depth.

1

The data model

Say this

“We added 47 fields across five objects in your sandbox. We changed nothing you already had.”

If they push

  • Fourteen fields on Account, three on Contact, twenty on Partner Influence, nine on the Portal Audit Log, one on Portal Settings.
  • Partner Influence is your object, not a new one. Four of its fields came straight from your own metadata export, so they match what Roman already uses. The rest are ours, added beside them.
  • The Portal Audit Log is the one genuinely new object. Nothing else in the org was renamed, retyped or removed.
  • Every field carries help text in Setup, so an admin who has never met this project can read what each one is for.

If they want to see it

Setup, Object Manager, Account, filter on Portal or Partner. The full 47-field table with help text is in the test script.

2

Certificate sign-in

Say this

“The service proves who it is with a certificate, the way an ID card works. There is no password anywhere in this system.”

If they push

  • The key pair was made outside Salesforce. The public half sits on the connected app in your org. The private half lives in the service’s secret store and never leaves it.
  • Salesforce checks the signature on every request for a session. A stolen copy of the public half is useless without the private half.
  • The certificate runs to December 2028. Replacing it is a configuration change, not a code change.
  • It signs in as one named integration user on an API-only profile, so everything the service does is attributable to that user.

If they want to see it

Setup, External Client App Manager, Partner Portal Tool Layer, then Settings, then OAuth Settings.

3

The tool layer

Say this

“One service, two doors, one set of rules. The portal calls it over the web. An agent calls the same thing over MCP. Both land in the same code.”

If they push

  • Thirteen actions are live. Every one is available through both doors from a single list, so a new action never has to be built twice.
  • Five more names are reserved for later weeks. Calling one of them is refused cleanly and recorded, rather than returning a confusing error.
  • The service holds no data of its own. It reads and writes Salesforce and keeps no copy.
  • This is the piece that makes the portal and an agent the same customer of the same rules. It was the part of the brief that asked for one layer everything routes through.

If they want to see it

The service health check reports its version and whether Salesforce is reachable.

4

Permissions and the rules it holds

Say this

“One table decides who is allowed to call what. Five kinds of caller, and nothing gets past it.”

If they push

  • The five: anonymous, partner, staff, account executive, agent.
  • Applying is anonymous only. The dashboard is partner only. The application queue is staff only. Agents can read and check conflicts, but cannot make a decision.
  • A second rule sits on top: a signed-in partner whose contract is not signed can only see who they are and their contract status. Nothing else opens until the contract is signed.
  • A refusal is a recorded event, not a silent failure. You can see every attempt that was turned down and who made it.

If they want to see it

Portal Audit Log, filter Outcome to Denied.

5

The audit log

Say this

“Every call writes one row, including the ones we refuse. There are 516 rows in the sandbox today.”

If they push

  • Nine columns: what was done, who did it, the outcome, the record it touched, a request id, the inputs with secrets stripped, and when.
  • Who is recorded two ways. A partner links to their Contact. A staff member links to their User. The blank one tells you which kind of caller it was.
  • Outcomes are Success, Denied or Error. Errors in the sandbox today are almost all the notification email failing, because sandbox email is switched off by default. The Salesforce record was still written.
  • The request id ties a row to the matching line in the service log, so a support question can be traced end to end.

If they want to see it

Portal Audit Log, All.

6

Hosting

Say this

“The portal is on Cloudflare Pages and the service is on Render. Both are swappable, and moving either one is a deploy change, not a rewrite.”

If they push

  • The portal is a plain static site. Any static host serves it. Nothing in it is tied to Cloudflare.
  • The service is a container. Any container host runs it. Nothing in it is tied to Render.
  • No code anywhere knows which host it is on. Addresses and secrets are configuration.
  • If you would rather it ran in your own accounts, that is a handover of configuration, not a rebuild. Say the word and we scope it.

If they want to see it

Both addresses are in the test script, and both are open right now.

The 47 fields, without memorising them

Do not list fields in a meeting. Speak to the five groups. Each group has one purpose, and that purpose is the answer to almost every question about it.

ObjectFieldsWhat the group is for
Account14The partner relationship: what type of partner, where they are in their lifecycle, when they applied and were approved, their commission rate, and the state of their contract.
Contact3Sign-in only: when they last signed in, the current link’s expiry, and a one-way hash of the link. The link itself is never stored.
Partner Influence20One deal registration: who registered it, for which customer, what they claim they did, what it is worth, and the decision with who made it and when.
Portal Audit Log9One row per call. The nine columns in item 5.
Portal Settings1A single switch: copy the deciding account executive’s manager on decision emails.

If anyone wants the field-by-field detail, it is in the test script, with every field’s help text, type, week, workstream and a link straight to it in Setup. Send that rather than reading it out.

Questions that are likely

QuestionAnswer
“Did you change anything of ours?”No. Every change is an addition. Nothing was renamed, retyped or removed, and that is a standing rule on the build, not a promise.
“Where does the data live?”In your sandbox. The service keeps no copy of anything.
“What if we pick a different esign tool?”Two fields hold the external id and the signing link. Changing tools is a webhook change, not a redesign. We still need your answer on which tool.
“Can our own agents call this?”Yes. That is the second door, and it is already live.
“Is any of this in production?”No. Everything so far is in the sandbox, by design.
“Who can reach the portal today?”Anyone with the address sees the landing and application pages. The dashboard needs an approved partner and an emailed sign-in link.
“How do we know it works?”166 automated test cases cover the service and the portal, and there is a 61-step script a person runs by hand. The link is in the notes below.

Say these plainly if they come up

  • Sandbox email is off by default, so notification emails only send while it is switched on for a session. The Salesforce records are written either way.
  • The commission definition is still open. The field exists and is empty until Factory defines it.
  • The esign tool is still open, and it is blocking the contract step from being finished properly.
  • Week 6 is specified but not approved, and nothing for it has been built.

Saying what is not finished is what makes the finished parts believable. Do not soften these.
