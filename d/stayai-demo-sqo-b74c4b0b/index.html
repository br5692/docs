Demo, SQO and Disqualified tracking on the Opportunity

Six new Opportunity fields and three flow changes that put a demo date, a demo status, a sales-qualified date and a disqualified date on every deal, separate deals lost before qualification from deals lost after it, and stop a deal leaving Pre Qualification without a real Amount. Built and proven in the sandbox, not yet in production.

02

What changed

Active in sandbox

Six fields, one Custom Metadata Type, one validation rule, two edited flows and one new flow. Nothing outside those was touched.

The six fields low level

Opportunity.Demo_Date__c
Date. Help text: "Date of the first booked demo (from the Chilipiper meeting)." Writable by hand.
Opportunity.Demo_Status__c
Restricted picklist. Scheduled, Completed, No Show, Cancelled. Restricted so no fifth value can be typed in by an integration.
Opportunity.Sales_Qualified_Date__c
Formula (Date). Date_Entered_Discovery__c first, then the earliest of the Solution Validation, Proposal, Verbal and Closed Won entry dates for legacy deals with no Discovery stamp.
Opportunity.Disqualified_Date__c
Formula (Date). Disqualified stage date first; then, for deals sitting at the Disqualified stage with no stamp, the Closed Lost date or Close Date; then the Closed Lost date for the two disqualification reasons. Full expression below.
Opportunity.Sales_Qualified__c
Formula (Checkbox). True once the deal has demonstrably reached Discovery or later, by stage-entry date or by current stage. The current-stage clauses are what keep pre-2023 deals honest, since the stage-date fields only start on 2023-04-12.
Opportunity.Amount_Is_Placeholder__c
Formula (Checkbox). True when the Amount still equals the configured placeholder and that placeholder is above zero. Full expression in section 02 below.
Opportunity_Default__mdt.Pre_Qual_Amount__c
Number(18,2) on the single Custom Metadata record named Default. Number rather than Currency because Custom Metadata Types do not support Currency fields. Seeded at 0.
// Disqualified_Date__c
IF(
  NOT(ISBLANK(Date_Entered_Disqualified__c)),
  Date_Entered_Disqualified__c,
  IF(
    ISPICKVAL(StageName, "Disqualified"),
    BLANKVALUE( Date_Entered_Closed_Lost__c, CloseDate ),
  IF(
    ISPICKVAL(StageName, "Closed Lost") &&
      ( ISPICKVAL(Closed_Lost_Reason__c, "Pre-Qual") || ISPICKVAL(Closed_Lost_Reason__c, "Disqualified") ),
    Date_Entered_Closed_Lost__c,
    NULL
  )
)
// Amount_Is_Placeholder__c
AND(
  $CustomMetadata.Opportunity_Default__mdt.Default.Pre_Qual_Amount__c > 0,
  NOT(ISBLANK(Amount)),
  Amount = $CustomMetadata.Opportunity_Default__mdt.Default.Pre_Qual_Amount__c
)

// Validation rule Amount_Required_To_Leave_Pre_Qual, error on the Amount field
// "Enter the real opportunity amount before moving past Pre Qualification."
AND(
  ISCHANGED(StageName),
  ISPICKVAL(PRIORVALUE(StageName), "Pre Qualification"),
  NOT(ISPICKVAL(StageName, "Closed Lost")),
  NOT(ISPICKVAL(StageName, "Disqualified")),
  OR(
    ISBLANK(Amount),
    Amount <= 0,
    AND(
      $CustomMetadata.Opportunity_Default__mdt.Default.Pre_Qual_Amount__c > 0,
      Amount = $CustomMetadata.Opportunity_Default__mdt.Default.Pre_Qual_Amount__c
    )
  )
)

Why the placeholder appears in both. A blank Amount and a placeholder Amount are the same problem wearing different clothes: nobody has said what the deal is worth. The rule treats them the same way, and the flag makes the second one visible in a report rather than hiding behind a real-looking number.

Field visibility. Read access on all six went to the ten profiles that carry real users: System Administrator, GTM - AE, GTM - General, GTM - Events, Leadership, CX - Success, CX - Onboarding, Partnerships, Sales and Solution Manager. Edit access on the two writable fields went to System Administrator, GTM - AE, GTM - General, GTM - Events and Leadership, so a rep can correct a demo status by hand. The three formula fields are read only by nature. This mirrors how Date_Entered_Discovery__c is granted today, with edit added where the request calls for manual correction.

Flow 1 of 3  ·  Opportunity [BS] - Stamp Stage Change v11 → v12

Before (v11). The before-save stamper handled seven stages: Pre Qualification, Discovery, Solution Validation, Proposal, Verbal, Closed Won and Closed Lost. Disqualified was missing, even though the stage is active on the Opportunity picklist and the field Date_Entered_Disqualified__c already existed. Every deal moved to Disqualified left that date blank.

After (v12). One new decision outcome and one new assignment, built on exactly the pattern the other stages use: fire only when the stage equals Disqualified and the date is still blank, so the first entry wins and a deal bounced back into the stage does not get restamped.

<!-- new decision outcome on Decision_Stage -->
+ <rules>
+     <name>Disqualified</name>
+     <conditions> $Record.StageName EqualTo "Disqualified" </conditions>
+     <conditions> $Record.Date_Entered_Disqualified__c IsBlank true </conditions>
+     <connector> Stamp_Disqualified </connector>
+ </rules>

<!-- new assignment -->
+ <assignments>
+     <name>Stamp_Disqualified</name>
+     <assignmentItems>
+         <assignToReference>$Record.Date_Entered_Disqualified__c</assignToReference>
+         <value><elementReference>$Flow.CurrentDate</elementReference></value>
+     </assignmentItems>
+ </assignments>

Read this as: the Disqualified branch is additive. The seven existing branches, the six existing helper formulas and the entry condition ISNEW() || ISCHANGED(StageName) are byte-identical to v11. Verified by diffing the deployed v12 against a fresh production retrieve of v11.

Flow 2 of 3  ·  Event - Process Chilipiper Event v6 → v7 → v8

Before (v6). When Chili Piper booked a demo on an account with no open Opportunity, this subflow created a Pre Qualification Opportunity with Next Step "Conduct Demo" and linked the event to it. The meeting date lived only on the event, so no report could group deals by when the demo happened.

After (v7). The Create Booked Demo Opportunity element now sets two more fields at creation. One new formula converts the meeting's start time to a calendar date. Nothing else in the subflow moved: the account lookup, the ownership branches, the open-Opportunity guard and the event association are untouched.

<!-- new formula -->
+ <formulas>
+     <name>fx_DemoDate</name>
+     <dataType>Date</dataType>
+     <expression>DATEVALUE( {!Event.StartDateTime} )</expression>
+ </formulas>

<!-- two new input assignments on Create_Booked_Demo_Opportunity -->
+ <inputAssignments><field>Demo_Date__c</field>
+     <value><elementReference>fx_DemoDate</elementReference></value></inputAssignments>
+ <inputAssignments><field>Demo_Status__c</field>
+     <value><stringValue>Scheduled</stringValue></value></inputAssignments>

One thing to know about the date. Inside a flow, DATEVALUE resolves against the time zone of the user whose save fires the flow, not GMT. Tested in the sandbox: a meeting starting 6:00 PM Pacific (01:00 GMT the next day) stamped the Pacific calendar day, not the following one. In production 285 of the 286 Chili Piper events were created by one America/Los_Angeles user, so the stamp follows the Pacific calendar day in practice. The one exception was created by an America/Dawson_Creek user, where a late-evening meeting could land a day either side. Worth knowing rather than worth blocking on.

Then v8, for the Pre-Qual Amount. One record lookup on the Custom Metadata record, one decision, one assignment, and one more field on the same create element. The decision is what keeps this inert: while the configured number is zero, the flow takes the default branch, the Amount variable is never set, and the Opportunity is created exactly as it was in v7.

<!-- Decision_Open_Opportunity default now routes through the lookup -->
<recordLookups>
    <name>Get_Opportunity_Defaults</name>
    <object>Opportunity_Default__mdt</object>
    <filters> DeveloperName EqualTo "Default" </filters>
    <connector> Decision_Pre_Qual_Amount </connector>
</recordLookups>

<decisions>
    <name>Decision_Pre_Qual_Amount</name>
    <rules> Get_Opportunity_Defaults.Pre_Qual_Amount__c GreaterThan 0
        → Set_Pre_Qual_Amount → Get_New_Business_Opp_Record_Type </rules>
    <defaultConnector> Get_New_Business_Opp_Record_Type </defaultConnector>
</decisions>

<!-- one more input assignment on Create_Booked_Demo_Opportunity -->
<inputAssignments><field>Amount</field>
    <value><elementReference>varPreQualAmount</elementReference></value></inputAssignments>

Read this as: the account lookup, the ownership branches, the open-Opportunity guard, the event association and the v7 demo assignments are all unchanged. The only new path is the one that reads the configured number.

Flow 3 of 3  ·  Event [AS] - Demo Status to Opportunity new, v4

Before. Nothing existed. Chili Piper writes Canceled_CP__c and No_Show_CP__c back onto the event, and those two facts died on the event record. Neither reached the Opportunity, so a pipeline report could not tell a demo that happened from one nobody showed up to.

After (v4). A record-triggered after-save flow on the Event, entered when the event is a Chili Piper event and its WhatId points at an Opportunity. It reads the Opportunity, takes one of four immediate branches, and carries a fifth branch on a scheduled path. Both Opportunity updates carry a fault path, so a failed update can never roll the Chili Piper event insert back and lose the booking.

BranchFires whenWrites
CancelledCanceled_CP__c = trueDemo Status = Cancelled
No ShowNo_Show_CP__c = trueDemo Status = No Show
Bookedneither flag set, and the Opportunity has no Demo Date yetDemo Date = meeting start date, Demo Status = Scheduled
Rebooked After Cancellationneither flag set, the Opportunity already has a Demo Date, and Demo Status is CancelledDemo Status = Scheduled. Demo Date deliberately untouched, so it keeps the first booked date
Day After Demoscheduled path, EndDateTime + 1 day, neither flag set, and Demo Status is still ScheduledDemo Status = Completed
 
<!-- entry criteria -->
<object>Event</object>
<recordTriggerType>CreateAndUpdate</recordTriggerType>
<triggerType>RecordAfterSave</triggerType>
<filters> Chilipiper_Event__c EqualTo true </filters>
<filters> WhatId StartsWith "006" </filters>

<!-- the Completed path -->
<scheduledPaths>
    <name>Day_After_Demo</name>
    <offsetNumber>1</offsetNumber>
    <offsetUnit>Days</offsetUnit>
    <recordField>EndDateTime</recordField>
    <timeSource>RecordField</timeSource>
</scheduledPaths>

Why Completed is guarded three ways. It writes only when the meeting was not cancelled, was not a no show, and the status has not already been changed by a rep. A rep who marks a demo No Show by hand at 4pm will not have it flipped back to Completed overnight.

One deliberate omission

The original plan also called for writing Demo Date and Demo Status inside the subflow's Associate Event with Opportunity step. That step updates the Event record, not the Opportunity, so Opportunity fields cannot be set there. The Booked branch of the new flow covers exactly that case: it fires the moment the event's WhatId is pointed at an Opportunity, whether by the subflow or by hand. No behaviour was lost.

Case e is the one worth noticing. Before this change, moving a deal to Disqualified left every date field blank, so the deal simply vanished from any date-based funnel report. It now stamps on the way in, and the Disqualified Date formula picks it up with no backfill.

Cases i and k are the pair that matters. A placeholder Amount stops a deal moving forward, and does not stop a deal being disqualified. That is the whole point of the exemption: chasing a real number is worth a blocked save, and clearing dead pipeline is not.

Cases k, l and s are the exemptions. Disqualifying a deal, losing it, or parking it in Nurture are never blocked by the Amount rule. Only a move forward out of Pre Qualification is. Nurture joined that list after the owner ruling below, and case s is the test that proves it rather than the formula that promises it.

Case m is the state this actually ships in. With the number still unset, a Chili Piper booking behaves exactly as it did before. Nothing turns on until someone types a number into the Custom Metadata record.

Case g cannot be run inside a session. The Completed path is a genuine one-day wait. What was verified is that the scheduled path exists on the active flow version, with the right offset and the right guard conditions. Watching one real demo roll over to Completed the day after is the confirming step, and it is the org owner's to run.

    What the review pass changed

    The build was re-scored line by line against the original request, with every claim checked against the org rather than against the deploy log. Five things changed. One. Sales Qualified read false on 243 production deals that had plainly been qualified: 165 Closed Lost or Disqualified deals that reached Solution Validation or beyond without a Discovery stamp, and 78 Closed Won deals with no stage dates at all. Those 165 were sitting inside the "lost without ever becoming SQO" bucket the request asked for, which made the bucket 20% wrong. The formula now reads later-stage dates and current stage as well. Two. Sales Qualified Date now falls back to the earliest later-stage date, so it is never blank where the box is ticked. Three. Disqualified Date was blank for 10 of the 12 deals sitting at the Disqualified stage, because the stage stamp only starts from this change; it now falls back to the Close Date for those. Four. A demo cancelled and then rebooked in Chili Piper stayed Cancelled forever; it now returns to Scheduled while keeping the first booked date. Five. Both Opportunity updates in the new flow now have a fault path, so a failed update cannot roll back the Chili Piper event insert and lose the booking.

    Four things worth an owner's eyes, none of them touched

    All four predate this work and were left exactly as found. Ensure_Opp_has_amount is an active validation rule that can never fire: it tests for the stages "Value Creation", "Technical Validation" and "Negotiation", none of which are on the Opportunity stage picklist any more. Its error message, "Enter an Amount before moving stage past discovery", describes the job the new rule now actually does. Disqualified__c is a checkbox with its own required-details rule and zero records using it, running in parallel with the Disqualified stage. Nurture is an active stage that the stage stamper never records: the flow carries an fx_NurtureDate formula that nothing uses, so Date_Entered_Nurture__c is never written. Five record updates in the Chili Piper subflow have no fault path, the same gap that was just closed in the new flow.

  • Two deploy-time steps beyond the metadata. First, set the Pre-Qual Amount in Setup once Chris gives the number, then run the one-time Amount pass over the 63 open Pre Qualification deals that have none. Decided from the org nine rulings

Nine of the eleven items that were open are now decided, because the org already answered them. Each carries the read-only production query that settled it, so any of them can be re-checked in a minute.

  • Disqualified Reason reuses Closed Lost Reason. No new field. 127 deals already carry Pre-Qual or Disqualified there, and the parallel Disqualified__c checkbox has 0 records, so a second field would split a live answer and inherit a dead one.
  • Disqualified Date is not one to one with the Closed Lost date. A straight copy would stamp a disqualification date on every ordinary loss: of 1,412 Closed Lost and Disqualified deals, 520 are Bad Timing and 173 Competition, against 127 that carry a disqualification reason. Only those 127 count.
  • Edit rights on Demo Status stay as built — Admin, GTM (AE, General, Events) and Leadership, with CX and Partnerships read only. Everyone who actually creates or edits the underlying records is covered: Chili Piper events are created by System Administrator (285) and Leadership (1), and the cancel and no-show edits were last touched by System Administrator (21) and GTM - AE (1). Worth knowing: Partnerships owns 56 of the 81 open Pre Qualification deals, more than any other profile, so they are the ones most likely to meet the Amount rule — they edit Amount, which is a standard field they already control.
  • Sales Qualified Date keeps its fallback. The strict copy would leave 165 flagged deals with a blank date. The literal one-to-one with Date Entered: Discovery still holds for all 1,644 deals that carry the stamp.
  • A second demo keeps the first date and the first outcome. A cancelled-then-rebooked demo returns to Scheduled. As built, proven by tests n, o and p.
  • Nurture is now exempt from the Amount rule, alongside Closed Lost and Disqualified, because parking a deal is not advancing it. Harmless to add: 0 deals sit in Nurture today. Changed in the sandbox this pass and re-tested; forward moves are still blocked.
  • Backfilling the 93 Opportunity-linked Chili Piper events is a deploy-time checklist step, not a question. Script and safety notes are in the promotion runbook.
  • The 160 Account-linked Chili Piper events stay out of scope for this pass. Flagged, not scheduled.
  • The Stage_Lost_Required_Fields exemption is left alone. It lets deals lost straight out of Pre Qualification skip a Closed Lost Reason — 190 carry none, 180 of which never reached Discovery — but the bucket keys on Sales Qualified rather than on the reason, so it is unaffected.
One question, and it is the only thing holding this up

What should the Pre-Qual placeholder Amount be? The Custom Metadata record ships at 0, which makes the whole placeholder path a no-op: nothing is stamped and the placeholder flag is false everywhere. One field edit in Setup turns it on, in the sandbox and later in production, with no deployment and no code change. The number matters because of the population behind it: 63 of the 81 open Pre Qualification deals in production have no usable Amount today, 61 blank and 2 at or below zero. Those are the records that would take the number in a one-time pass. Until it is chosen, the only live piece is the validation rule.
