Demo, SQO and Disqualified tracking on the Opportunity

Six new Opportunity fields and three flow changes that put a demo date, a demo status, a sales-qualified date and a disqualified date on every deal, separate deals lost before qualification from deals lost after it, and stop a deal leaving Pre Qualification without a real Amount. Built and proven in the sandbox, not yet in production.

02

What changed

Active in sandbox

Six fields, one Custom Metadata Type, one validation rule, two edited flows and one new flow. Every element below was read back out of the two orgs on 11 September and walked one at a time, so each change can be opened in Flow Builder and checked by hand.

The six fields low level

Opportunity.Demo_Date__c
Date. Help text: "Date of the first booked demo (from the Chilipiper meeting)." Writable by hand.
Opportunity.Demo_Status__c
Restricted picklist. Scheduled, Completed, No Show, Cancelled, in that order. Restricted so no fifth value can be typed in by an integration. The field description was corrected on 11 September and now names the split: a manual value survives the Completed and re-booking paths, which act only on a status of Scheduled or Cancelled, and a later Chili Piper cancellation or no show still overwrites it.
Opportunity.Sales_Qualified_Date__c
Formula (Date). Date_Entered_Discovery__c first, then the earliest of the Solution Validation, Proposal, Verbal and Closed Won entry dates for legacy deals with no Discovery stamp. The field description was corrected on 11 September and now names the one exception: 78 Closed Won Opportunities in production predate the stage-date fields entirely, so Sales Qualified is true on them while this date stays blank.
Opportunity.Disqualified_Date__c
Formula (Date). Disqualified stage date first, then, for deals sitting at the Disqualified stage with no stamp, the Closed Lost date or Close Date, then the Closed Lost date for the two disqualification reasons. Full expression below.
Opportunity.Sales_Qualified__c
Formula (Checkbox). True once the deal has demonstrably reached Discovery or later, by stage-entry date or by current stage. The current-stage clauses are what keep pre-2023 deals honest, since the stage-date fields only start on 2023-04-12.
Opportunity.Amount_Is_Placeholder__c
Formula (Checkbox). True when the Amount still equals the configured placeholder and that placeholder is above zero. Full expression below.
Opportunity_Default__mdt.Pre_Qual_Amount__c
Number(18,2) on the single Custom Metadata record named Default. Number rather than Currency because Custom Metadata Types do not support Currency fields. Seeded at 0.

Why the placeholder appears in both. A blank Amount and a placeholder Amount are the same problem wearing different clothes: nobody has said what the deal is worth. The rule treats them the same way, and the flag makes the second one visible in a report rather than hiding behind a real-looking number.

Five existing fields travel with the build as reference only. Date_Entered_Discovery__c, Date_Entered_Disqualified__c, Date_Entered_Closed_Lost__c, Closed_Lost_Reason__c and Disqualified__c were pulled from production so the new formulas could be written against their real definitions. Each was diffed against a fresh production retrieve on 11 September and all five are unchanged, byte for byte. Nothing in this build alters an existing field.

Field visibility. Read access on all six went to the ten profiles that carry real users: System Administrator, GTM - AE, GTM - General, GTM - Events, Leadership, CX - Success, CX - Onboarding, Partnerships, Sales and Solution Manager. Edit access on the two writable fields went to System Administrator, GTM - AE, GTM - General, GTM - Events and Leadership, so a rep can correct a demo status by hand. The three formula fields are read only by nature. This mirrors how Date_Entered_Discovery__c is granted today, with edit added where the request calls for manual correction.

Two flows carry no changes at all

Contact [AS] - Process Chilipiper Event and Event [AS] - Process Chilipiper Event are version 1 in both orgs and untouched. They ride along on the branch only so the flow scanner can read the whole Chili Piper chain in one pass. They are not walked below because nothing in them moved.

Flow 1 of 3  ·  Opportunity [BS] - Stamp Stage Change v11 → v12

A before-save flow on the Opportunity that writes a date field the first time a deal reaches each stage. Entry condition ISNEW() || ISCHANGED(StageName), unchanged. Two elements moved. Everything else is identical to the production version.

Before (v11, production, flow id 301VV00000jpRsOYAU). The Decision - Stage element fans out to seven stage branches and a Default Outcome: Pre Qualification, Discovery, Solution Validation, Proposal, Verbal, Closed Won, Closed Lost. There is no Disqualified branch, so a deal moved to the Disqualified stage falls to Default Outcome and no date is written. Date_Entered_Disqualified__c already existed on the object and was simply never filled.

After (v12, sandbox, flow id 301cb00001C1yITAAZ). One new branch, Disqualified, sits between Closed Lost and Default Outcome, feeding one new assignment. The other seven branches, the six helper formulas and the entry condition are byte-identical to v11, confirmed by diffing the two versions element by element.

Flow 2 of 3  ·  Event - Process Chilipiper Event v6 → v8

The autolaunched subflow that runs when Chili Piper books a meeting. It finds the contact and account, sets ownership, and, when the account has no open Opportunity, creates a Pre Qualification Opportunity and links the meeting to it. Seven elements are involved in the change: two existing ones altered, five added. The account lookup, the ownership branches, the open-Opportunity guard and the event association are untouched.

Before (v6, production, flow id 301VV00000kIL8OYAW). Follow the right-hand leg down from Decision - Open Opportunity. Its Default Outcome, meaning the account has no open Opportunity, goes straight to Get New Business Opp Record Type, then Create Booked Demo Opportunity, then the two steps that point the meeting at the new deal. The meeting date lives only on the Event record, so no Opportunity report can group deals by when the demo happened.

After (v8, sandbox, flow id 301cb00001C4rmKAAR). The same leg now passes through two extra steps before reaching the record-type lookup: Get Opportunity Defaults, then Decision - Pre Qual Amount, whose left branch runs Set Pre Qual Amount and whose right branch skips straight past it. Both branches rejoin at Get New Business Opp Record Type, so a deal is created either way.

Opening Create Booked Demo Opportunity shows Opportunity Amount taking varPreQualAmount, Demo Date taking fx_DemoDate and Demo Status taking the literal Scheduled, sitting alongside the nine values that were already there. This is the single place where a booked demo picks up all three at once.

Which asks this serves. "Demo Date (date the first call is booked for)" and "Demo Status (Scheduled, Completed, No Show, Cancelled)" for the two demo values, and "I think for now I'm just going to pick a # and set process that the opp owner manually adds the amount" for the Amount. The number is read from a record rather than written into the flow, so picking it later costs one field edit in Setup.

One thing to know about the date. Inside a flow, DATEVALUE resolves against the time zone of the user whose save fires the flow, not GMT. Tested in the sandbox on 11 September: a meeting starting 6:00 PM Pacific, which is 01:00 GMT the next day, stamped the Pacific calendar day. In production 285 of the 286 Chili Piper events were created by one America/Los_Angeles user, so the stamp follows the Pacific calendar day in practice. The single exception was created by an America/Dawson_Creek user, where a late-evening meeting could land a day either side. Worth knowing rather than worth blocking on.

Flow 3 of 3  ·  Event [AS] - Demo Status to Opportunity new, v4

This flow did not exist in production. Chili Piper writes Canceled_CP__c and No_Show_CP__c back onto the Event, and before this build those two facts died on the Event record. Neither reached the Opportunity, so a pipeline report could not tell a demo that happened from one nobody showed up to. The whole flow is walked below, start to finish, so it can be reproduced from this page.

The whole flow (v4, sandbox, flow id 301cb00001C6LlfAAF). Two legs hang off the Start element. One deliberate omission

The original plan also called for writing Demo Date and Demo Status inside the subflow's Associate Event with Opportunity step. That step updates the Event record, not the Opportunity, so Opportunity fields cannot be set there. The Booked branch of this flow covers exactly that case: it fires the moment the meeting's WhatId is pointed at an Opportunity, whether by the subflow or by hand. No behaviour was lost.

Case e is the one worth noticing. Before this change, moving a deal to Disqualified left every date field blank, so the deal vanished from any date-based funnel report. It now stamps on the way in, and the Disqualified Date formula picks it up with no backfill.

Cases i and k are the pair that matters. A placeholder Amount stops a deal moving forward, and does not stop a deal being disqualified. Chasing a real number is worth a blocked save, and clearing dead pipeline is not.

Case m is the state this actually ships in. With the number still unset, a Chili Piper booking behaves exactly as it did before. Nothing turns on until someone types a number into the Custom Metadata record.

Case g cannot be run inside a session. The Completed path is a genuine one-day wait. What was verified is that the scheduled path exists on the active flow version with the right offset and the right guards. Watching one real demo roll over to Completed the day after is the confirming step, and it belongs to whoever owns the org.

What the 11 September pass changed high level

The build was re-scored line by line against both the original written request and the 10 September call, with every claim checked against the org rather than against a deploy log. No flow logic, field type or validation-rule formula moved. The three flows are still v12, v8 and v4, and the placeholder is still 0. Three things were corrected.

Decided from the org nine rulings

Nine items that were open are decided, because the org already answered them. Each carries a read-only production count that settled it, so any of them can be re-checked in a minute.

  • Disqualified Reason reuses Closed Lost Reason. No new field. 127 deals already carry Pre-Qual or Disqualified there, and the parallel Disqualified__c checkbox has 0 records, so a second field would split a live answer and inherit a dead one.
  • Disqualified Date is not one to one with the Closed Lost date. A straight copy would stamp a disqualification date on every ordinary loss: of 1,412 Closed Lost and Disqualified deals, 520 are Bad Timing and 173 Competition, against 127 that carry a disqualification reason. Only those 127 count.
  • Edit rights on Demo Status stay as built. Admin, GTM (AE, General, Events) and Leadership, with CX and Partnerships read only. Everyone who creates or edits the underlying records is covered: Chili Piper events are created by System Administrator (285) and Leadership (1), and the cancel and no-show edits were last touched by System Administrator (21) and GTM - AE (1). Worth knowing: Partnerships owns 56 of the 81 open Pre Qualification deals, more than any other profile, so they are the ones most likely to meet the Amount rule. They edit Amount, which is a standard field they already control.
  • Sales Qualified Date keeps its fallback. A strict copy would leave 165 flagged deals with a blank date. The literal one-to-one with Date Entered: Discovery still holds for all 1,644 deals that carry the stamp.
  • A second demo keeps the first date and the first outcome. A cancelled-then-rebooked demo returns to Scheduled. As built, proven by cases n, o and p.
  • Nurture is exempt from the Amount rule, alongside Closed Lost and Disqualified, because parking a deal is not advancing it. Harmless to add: 0 deals sit in Nurture today in either org. Forward moves are still blocked, proven by case i.
  • Backfilling the 93 Opportunity-linked Chili Piper events is a deploy-time checklist step, not a question. Script and safety notes are in the promotion runbook.
  • The 160 Account-linked Chili Piper events stay out of scope for this pass. Flagged, not scheduled.
  • The Stage_Lost_Required_Fields exemption is left alone. It lets deals lost straight out of Pre Qualification skip a Closed Lost Reason, and 190 carry none, 180 of which never reached Discovery. The bucket keys on Sales Qualified rather than on the reason, so it is unaffected.
Four things worth an owner's eyes, none of them touched

All four predate this work and were left exactly as found. Ensure_Opp_has_amount is an active validation rule that can never fire: it tests for the stages "Value Creation", "Technical Validation" and "Negotiation", none of which are on the Opportunity stage picklist any more. Its error message, "Enter an Amount before moving stage past discovery", describes the job the new rule now actually does. Disqualified__c is a checkbox with its own required-details rule and zero records using it, running in parallel with the Disqualified stage. Discovery_Completed__c is a third dead parallel path, also zero records, that a report author could reach for instead of Sales Qualified. Five record updates in the Chili Piper subflow have no fault path, the same gap that was closed in the new flow.

Open for a decision three items

1 · The Pre-Qual placeholder Amount number

The Custom Metadata record ships at 0, which makes the whole placeholder path a no-op: nothing is stamped and the placeholder flag is false everywhere. One field edit in Setup turns it on, in either org, with no deployment and no code change. The population behind it: 63 of the 81 open Pre Qualification deals in production have no usable Amount today, 61 blank and 2 at or below zero. Those are the records a one-time pass would fill.

2 · What a Chili Piper cancellation should do to a manually set Demo Status

Proven by case u: a rep's manual Completed is overwritten to Cancelled when Chili Piper cancels the meeting. The build treats the Chili Piper flags as authoritative, which is defensible, but it was never a stated decision. The choice is to keep Chili Piper authoritative, or to guard the cancel and no-show branches the way the Completed and re-booking branches are already guarded.

3 · Nurture is a two-step way around the Amount requirement

Proven by case v: Pre Qualification to Nurture to Discovery is allowed with a blank Amount, because on the second move the prior stage is Nurture rather than Pre Qualification. The deal lands in Discovery, Sales Qualified, with no Amount. Inert today, since 0 deals sit in Nurture in either org, but it opens the moment anyone parks a deal. The choice is to leave it, on the basis that Nurture is a genuine pause and the Amount can be caught later, or to make the rule fire on the move into Discovery and beyond regardless of the prior stage. The second option also starts blocking existing deals that have never had an Amount, so it is not a free change.
