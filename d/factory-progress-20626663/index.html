Week 1: Foundation

built 2026-09-15, ready to test

Workstream 1, Portal Infrastructure. The parts every later week stands on: hosting, the Salesforce data model, one integration user with certificate sign-on, and the web service that every call goes through.

RequirementWhat was builtHow it worksProof
HostingThe portal on Cloudflare Pages. The web service on Render. Both deploy from the code repository on every push.The portal is static files with no secrets. The web service is one container with a health check that reports the running commit. Secrets live only in the Render environment.Both hosts confirmed through their own APIs. Health check green.
Data modelFactory's exported objects deployed unchanged. Portal fields added on Account, Contact and the Partner Influence junction. A new audit object.Every portal field carries a Portal or Partner prefix and help text. Factory's own fields, layouts and flows are never changed. The audit object holds one row per call.Field count matched by describe. Deploy records in the sandbox setup audit trail.
Integration userOne API-only user with a permission set that grants exactly the fields the portal uses.Least privilege: no profile changes, no admin rights. Every read or write the portal makes runs as this user, so every change in Salesforce traces to it.Permission set contents reviewed line by line. The user cannot log in through the browser.
Certificate sign-onAn External Client App with a certificate. The web service signs a short-lived token with the private key and exchanges it for a session.No password exists anywhere. The private key lives only in the Render environment. Salesforce trusts the certificate, not a secret string.Token exchange proven live. Certificate page in the sandbox.
Web service with audit logA Node service that exposes the same actions two ways: plain HTTP for the portal, and MCP for agents.Every call resolves who is calling, checks a permission table, validates the input, calls Salesforce as the integration user, and writes one audit row with the actor, outcome and request id. Refusals are audited too.Contract tests run against the sandbox and clean up after themselves. A live call shows its audit row within seconds.
Runs anywhereThe same container runs on a laptop against the same sandbox.One environment file selects the sandbox, the certificate and the mail transport. Nothing else changes between a laptop and Render.Container started locally, health check green, one audited call.

Week 2: Registration and sign-in

built 2026-09-16, ready to test

Workstream 2, Partner Registration, and the sign-in and dashboard lines of Workstream 1. A partner applies, Factory reviews and approves inside Salesforce, the invite goes out, the partner signs in with a link.

RequirementWhat was builtHow it worksProof
Initial request of partner statusA public application form on the portal.Six fields and an optional note. Submitting creates the Account as Applied and the Contact, and stamps the applied-at time. A hidden trap field and a duplicate check keep out bots and repeats.Live on the hosted portal. Account and audit row created.
Account and Contact creationDone by the web service on submit.Standard objects. The Account carries the application status, partner type and note. The Contact becomes the primary contact.Contract tests. Records visible in the sandbox.
Partner validation by FactoryA Partner Applications tab in the Factory Sales app with a decision flow.Operators see pending applications in a list and approve or deny with a note. Approve stamps the accepted-at time and moves the Account to Approved. Approve is refused until a primary contact exists.Walked through as a test operator. Audit row per decision.
Review list gated by permissionA custom permission that controls who sees the tab.Operators hold a permission set with the custom permission. A user without it does not see the tab.Proven with a second test user who has no access.
Pre-approved partner inviteApproval sends the invite automatically.A flow fires when the status turns Approved, sends the invite email from a Salesforce template, and writes an audit row. A pre-approved partner is simply created as Approved by the operator.Email rendered from the real template. Audit row partner_invite.
Log inEmail link sign-in, no password.The partner enters an email address. The reply is the same for every address. If the address belongs to an approved partner, a one-time link arrives, valid for fifteen minutes. Clicking it sets a secure cookie. Five requests per address and twenty per network address per hour.Live on the hosted portal. Second use of a link refused.
Partner dashboard shellThe signed-in home page with navigation.Shows the partner's company, a contract card and the registrations list. The list is empty until Week 4 fills it.Live on the hosted portal.
Application and acceptance timestampsTwo date-time fields on the Account.Applied-at set on submit. Accepted-at set on approve.Visible on the review page.
Operator permission setOne permission set for Factory operators.Read and edit on the portal fields, the custom permission, the tab and the flow. No profile changes.Assigned to the test operator; verified through the tab.

Week 3: Contract signature

built 2026-09-16, ready to test

Workstream 2, the partner contract line. Built so the e-sign tool can be plugged in later without touching anything else.

RequirementWhat was builtHow it worksProof
E-sign linkA Send Partner Contract action in Salesforce and a contract page in the portal.The operator pastes the signing link from the e-sign tool and clicks Send. The Account moves to Sent, an email tells the partner, and the portal's contract page shows a button that opens the link.Walked through on the hosted stack. Email rendered from the template.
Status syncContract status on the Account: Not Sent, Sent, Signed. Sent-at and signed-at times.A Mark Contract Signed action sets Signed. Flows on each change send the matching email and write an audit row. A webhook route is ready for the e-sign tool to report Sent and Signed on its own once the tool is named.Audit rows contract_sent and contract_signed. Webhook refuses unknown providers and bad signatures.
Status trackingThe portal reads the contract status through the web service.The contract card on the dashboard and the contract page show the current state. An optional gate confines a signed-in partner to the contract page until Signed. Off by default.Gate tested both ways.
Waiting on Factory. Which e-sign tool Factory uses. Until then the operator pastes the link by hand and marks Signed by hand. Plugging in the tool is one contained change with its own test.

Week 5: Deal decisions

built 2026-09-17, ready to test

Workstream 3, the decision half. The Factory account executive decides each registration inside Salesforce, the partner sees the decision and four numbers on the dashboard, and the multi-partner rules are enforced at decision time.

RequirementWhat was builtHow it worksState
AE approve, deny, needs informationA decision box on the operator page, next to the pending registrations list.Pick a registration, choose the outcome, add a note. Approve stamps who decided and when. Needs information sends the registration back to the partner with the note. A decided list sits beside the pending one.Built
Multi-partner and reseller rulesA conflict check that runs before every approval.One primary partner per deal. A second partner of the same type on the same deal is blocked with one sentence and nothing is written. The rule lives in one place so Factory can change it later.Built
Decision emailsThree templates and one flow.Approved, denied and needs-information emails go to the partner from the sender address in one setting. An optional copy to the manager is off by default. Every send, including a failed one, writes an audit row and never undoes the decision.Built
Status write-back to the partnerThe decision on the registration detail page.Status, the note and the decision date. Who decided is never shown to the partner. A needs-information registration gets a reply box; the reply is stored on the registration and the operator sees it.Built
Dashboard tilesFour numbers above the registrations list.Pending, approved value, decided count and the approval rate over the last ninety days, computed from the partner's own registrations only.Built
Only the decision permission can decideOne custom permission.The decision box and the decided list appear only for operators who hold it. Everyone else sees the page as it was in Week 4.Built
Hidden until Factory wants itThe week toggle covers Week 5.The main portal address carries none of the Week 5 screens or text. The preview address shows all of it.Built, both addresses checked

Open questions for Factory

None of these blocks the build. Each has a working assumption and a single place to change when answered. Updated 2026-09-17 after a review of Weeks 1 to 3 against the plan and the call notes.

  • E-sign tool. Which tool Factory uses. Assumed: manual link until named.
  • One person, two partners. Can one contact act for more than one partner company. Assumed: one contact per email, one company per session.
  • Lifecycle stage on signature. Whether a signed contract moves the Account's lifecycle stage, and to which. Assumed: no change.
  • Opportunity page. Whether a Partner Influence related list may be added to Factory's Opportunity layout. Assumed: not yet.
  • New customers. Whether leadership wants a queue or an alert instead of the unassigned list. Assumed: the list.
  • Commission and partner tier. The commission definition and where partner tier lives. Needed for Week 6 tiles, not before.
  • Our components on Factory's page layouts. Whether we may add our own actions, field sections and one related list to the Account, Opportunity and Partner Influence layouts. Until answered, six things live on our own tab instead of the records.
  • What "accepted" means. The plan stamps acceptance when the contract is signed and sets a partner status on the Contact; the build stamps it at operator approval and keeps status on the Account. Assumed: approval.
  • Where the portal lives on factory.com. A page inside the marketing site or a separate site, and who routes to it. Assumed: a standalone site linked from the partner page.
  • Design kit. Factory's design team provides the kit; the Week 2 screens page stands in for the wireframe. Assumed: placeholders until it lands, polish before UAT.
