One service, two doors

running

The portal and an agent are the same customer of the same rules. Both doors reach one function, so permissions and logging cannot drift apart between them.

Portalbrowser · session cookie · POST /actions/:name
AgentMCP client · bearer key · POST /mcp
↓
dispatchActionone function: the permission table, the week gate, one audit row
↓
Salesforceread and write, Factory’s own org

Low level

  • MCP is not a second server. It is a second endpoint in the same process, and its tool list is generated from the same action list that serves the web door.
  • A new action appears in both doors from one place. It cannot exist in one and not the other.
  • The service stores nothing. It reads and writes Salesforce and keeps no copy of any data.
  • Five reserved action names answer with a recorded refusal rather than an unknown-action error, so a caller ahead of the build gets a clear answer.

Open it The health check reports the exact commit running and whether Salesforce is reachable.

Certificate sign-on

running

No password exists anywhere in this system. The service proves who it is with a certificate, the way an ID card works.

1. Key pair made outside Salesforceprivate half never enters the org
↓
2. Public certificate sits on the connected appExternal Client App, named-user JWT enabled
↓
3. Service signs a short-lived tokenprivate key held in its secret store
↓
4. Salesforce verifies and returns a sessionas one named API-only user

Low level

  • Subject CN=Partner Portal Tool Layer, O=Domestique, valid to 18 December 2028. Replacing it is a configuration change, not a code change.
  • The public half on its own is useless to anyone who copies it. Only the private key can produce a valid signature.
  • The integration user sits on an API-only profile with one permission set. Every write the service makes is attributable to that user.
  • Three certificate records in Certificate and Key Management are provisioning leftovers and are used by nothing. The live certificate is held inline on the app.

Open it External Client App Manager, Partner Portal Tool Layer, then Settings, then OAuth Settings.

4

Callers and rules

enforced

One table decides who may call what. There are five kinds of caller and nothing gets past the table.

CallerWhat it isWhat it may reach
anonymousNobody is signed in.Apply, request a sign-in link, open a sign-in link. Nothing else.
partnerA Contact at an approved partner, holding a signed session cookie.Their own account's data only. Never another partner's.
staffA Factory user with a bearer key.The review queues and the applications.
account executiveA Factory user with a bearer key, marked as an AE.Everything staff may do, plus the deal decisions.
agentAn automation holding a bearer key.Reads and conflict checks. Never a decision.

Rules that sit on top

  • A partner whose contract is not signed can only see who they are and their contract status. Every other partner action is refused. The gate is a switch, off until Week 3.
  • A partner is scoped to their own account by the query itself, not by the page. Asking for another partner’s registration returns nothing.
  • Sign-in requires both the company and the person to be approved.
  • Every refusal writes an audit row with the reason. Nothing fails silently.
  • Sign-in requests are capped at five per email an hour and twenty per address an hour.

Open it Portal Audit Log with Outcome filtered to Denied shows the table doing its job.

The audit log

running

Every call writes exactly one row, including the ones that are refused.

ColumnWhat it holds
Occurred AtWhen it ran.
ActionWhat was called.
OutcomeSuccess, Denied or Error.
Partner ContactThe partner who made the call.
Salesforce UserThe Salesforce user who made the call.
CallerThe raw identity behind those two.
RecordA link to the record the row acted on.
Request IDJoins the row to the matching line in the service log.
InputsWhat was sent in, with secrets stripped.

Only one of Partner Contact and Salesforce User is ever filled. Which one tells you whether a partner or a member of staff made the call. A partner is a Contact and never a Salesforce user, so partners never consume a licence.

Hosting

SalesforceFactory’s org
  • The portal is plain static files. Any static host serves it.
  • The service is a container. Any container host runs it.
  • Nothing in the code knows which host it is on. Addresses and secrets are configuration.
  • Moving either into Factory’s own accounts is a handover of configuration, not a rebuild.
  • The health address reports the running commit, so what is deployed is never in doubt.

The data model

additive only

Forty-nine fields across five objects, every one an addition. Nothing Factory already had was renamed, retyped or removed.

ObjectFieldsWhat the group is for
Account14Partner type, lifecycle stage, applied and approved dates, commission rate, contract state, the decision note and the primary contact.
Contact4Portal access status, plus the three sign-in fields: a one-way hash of the current link, its expiry, and the last sign-in.
Partner Influence20One deal registration: who registered it, for which customer, what they claim, what it is worth, and the decision.
Portal Audit Log10One row per call. Nine columns plus a link to the record touched.
Portal Settings1One switch: copy the deciding account executive's manager on decision emails.
  • Partner Influence is Factory’s own object. Four of its fields came from their metadata export and match what their team already uses.
  • The Portal Audit Log is the only genuinely new object.
  • Every field carries help text in Setup, so an admin who has never met this project can read what each one is for.

Open it Object Manager, Account, filtered on Portal or Partner. The full field-by-field table with help text and a Setup link each is in the manual test script.
