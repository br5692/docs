Decisions needing sign-off

10 pending review

Each shapes the product or is hard to reverse. Each card carries the ruling, the reasoning, and the discussion from 2026-09-16. Mark each one approved, changed, or questioned.

W1-1 The integration user identity

Decided
The portal talks to Salesforce as one integration user on the "Minimum Access - Salesforce - With API Permission" profile, not on the Salesforce Integration license.
Why
The Integration license cannot hold rights on Opportunity and other Sales Cloud objects the portal needs from Week 4.
Reversible
Yes, a profile swap.
Discussion
Two permission sets carry everything else: the integration set (objects and fields the portal reads and writes, Send Email, Edit Tasks as a platform dependency) and the operator set for Factory staff. View Roles was added to both because Factory's own account-transfer trigger reads the user's role on every Account update.

W1-4 Certificate-based authentication security

Decided
The tool layer signs a short-lived token with its private key for each Salesforce session. Salesforce checks it against the certificate on the External Client App. No password exists anywhere.
Why
This is the Salesforce-recommended pattern for server-to-server integrations (the JWT bearer flow). Rotation is a new key pair, a new certificate upload, and a key swap on Render.
Reversible
Yes.
Discussion
Question raised: is this best practice? Yes. It is the standard choice for a headless server, and it avoids storing a user password or a refresh token.

W2-2 Who may sign in access

Decided
Any partner whose Account status is Approved can sign in. A signed contract is not required until Week 3, behind a switch that is off by default.
Why
Contract signature is a Week 3 deliverable and the demo needs sign-in first.
Reversible
Yes, one environment variable.
Discussion
How approval happens: one field on the Account is set to Approved by the Approve button, by the decision screen on the review page, or by an admin editing the field. The flip stamps the accepted-at time and sends the invite email to the primary contact. Sign-in checks that one field and nothing else this week.

W2-5 Rate limits on sign-in requests abuse control

Decided
Two separate hourly counters. Per email address: the sixth request for the same address within an hour is refused. Per network address: the twenty-first request from the same IP within an hour is refused, whatever the emails. A refusal is a 429 with a retry-after time and an audit row.
Why
The email limit stops one partner being flooded with links. The IP limit stops one machine probing many addresses to learn who is a partner.
Reversible
Yes, two environment variables.
Discussion
Counters live in the tool layer's memory. They reset an hour after the first request, or whenever Render restarts the service. Render's forwarded address is trusted as the client address.

W2-6 Email transport on the hosted stack stopgap

Decided
The hosted tool layer writes each email to its log instead of sending, until sandbox deliverability is opened.
Why
The sandbox setting "System email only" blocks every email that code or a flow sends. The log gives the real subject, body, and a working link for testing.
Reversible
Yes, one environment variable.
Discussion
Blair's ruling on 2026-09-16: not staying here. Deliverability is flipped to "All email" for the real-path test and for the demo. The automation audit (section 04) found no Apex or workflow senders and no active flow that emails on Account or Contact, so the flip is safe when tests write only test records and send to owned addresses.

W2-7 The identity model data

Decided
One Contact per email, one Account per session. If two contacts share an email under approved partners, the one that signed in most recently wins, then the oldest record.
Why
Keeps the MVP simple. A contact at two partners is a business question for Factory (OQ-10, drafted in section 04).
Reversible
Yes.
Discussion
"One contact per email" is not a database rule. At sign-in the tool layer looks up Contacts by email under Approved accounts, applies the tie-break, and writes the candidate count to the audit row. Duplicates are tolerated, not prevented. "One account per session" is enforced by the session cookie itself, which carries exactly one contact id and one account id, signed by the server. Every later request reads the account from the cookie.

W2-11 Email templates belong to Factory ownership

Decided
The sign-in and invite emails are Salesforce email templates. The tool layer only fills in the first name and the link and sends through the org-wide sender address.
Why
Factory controls the words without a code change.
Reversible
Yes.
Discussion
The template must keep its two placeholders. The tool layer refuses to start if the sign-in template has lost the link placeholder, so a bad edit is caught at boot, not at send.

W2-12 Approve requires a primary contact rule

Decided
The Approve button refuses if the Account has no primary contact.
Why
Approval sends the invite email, and the invite needs a person. Without a contact there is nobody to email and nobody who could ever sign in, so the approval would create a partner nobody can use.
Reversible
Yes.
Discussion
Applications from the public form always set the primary contact, so staff only meet this rule on accounts created by hand.

W2-15 Tool names naming

Decided
Tool names are fixed. The Week 2 names replaced the Week 1 table, check_conflicts is reserved for deal conflicts in Week 4, and no aliases exist.
Why
One name per action, so every caller and every audit row means the same thing.
Reversible
Cheap today, costly later.
Discussion
Renaming costs nothing while no outside caller uses the names. It becomes expensive the day Factory's Droid prompts or agent configs reference a name, because those cannot be updated from here. Blair asked for a design that keeps renames cheap. Answer: an alias map in the tool layer, so an old name keeps working, is marked deprecated in the tool list, and is audited under the new name. Assigned to the builder 2026-09-16. With it in place, the ruling becomes "stable by default", not "fixed for good".

W2-17 + W2-26 The operator permission set permissions

Decided
Factory staff who review applications get: read and edit on Account and Contact (no create, no delete), read on Partner Influence, the review page and its tab, the decision flow, Lightning access, read on the Account website field, Run Flows, and View Roles.
Why
Staff review and approve. They do not create or delete records from the portal side. The last four grants were forced by the sandbox profile, the org's flow restriction, and Factory's account-transfer trigger, each recorded in the runbook with its deploy id.
Reversible
Yes, each grant is one line in the permission set.
Discussion
Blair agreed with the model and asked whether Factory should sign it off. Yes. It is the one decision that says what Factory's own staff can do, and it belongs in the note to Roman as "please confirm", half a page: this set, and the integration user's set.

Open with Factory

3 questions

Items that need a word from Factory, with the recommended default in each case so nothing blocks the build.

Email deliverability in the sandbox OQ-8

Setting: "System email only", which blocks the sign-in link and the invite email. Blair's ruling: flip to "All email" for the real-path test and the Tuesday demo, and mention it to Factory on the day.

Automation audit, 2026-09-16

0 of 340 Apex classes send mail (managed-package bodies not inspectable). 0 workflow email alerts. 3 active flows with an email step: Lead routing (fires on Lead create, emails the internal owner), a campaign alert (fires on one campaign's members), and the portal's own invite flow. Nothing fires on Account or Contact, the only Factory objects the tests write. 134 of 147 active users carry the sandbox ".invalid" suffix; the 13 real addresses are admins and system users. Roman last logged in 2026-09-10. Verdict: safe to flip while tests write only [TEST] records and send to owned addresses.

Approve and Deny on Factory's Account page OQ-9

The two quick actions exist as metadata. Placing them on Factory's Account page layout needs Factory's yes. Default: do not ask until Factory has seen the review page, where both actions already work. Also for the note: Factory's account-transfer trigger reads the user's role on every Account update, so the integration user and the operator set carry View Roles.

One person at two partners OQ-10

Draft question, ready to send:

Can one person be the contact for more than one partner company? For example, a consultant who works with two partners. Today, if the same email address exists under two approved partners, the portal signs them in to the one they used most recently. If this can happen, tell us how you would like it handled: always ask which company, or one company per email address.

Contract e-signature Week 3

No e-signature package is installed in the sandbox (installed: ZoomInfo, Gong, Granola, Sales Insights, Linear, a rollup tool). Whatever Factory signs with lives outside Salesforce. Default for Week 3: the plan's fallback, a signed-PDF reference on the Account with a status field, which works with any tool named later. Ask on demo day what they sign with.

Also agreed 2026-09-16

  • Demo with placeholder copy. Factory's words can replace it after they see it.
  • No access offered to Factory yet. Demo only. Access on request.
  • Help text on Factory's six fields (OQ-6): proceed in the sandbox, production waits on Factory.
  • Commission definition and UAT ownership: later communications, not needed before the demo.
